## What was kept

Each line: what changed, then its own measurement against its parent commit (paired, 50 corpus
positions at 100 000 unless said), every move and value equal.

1. **Column lanes written in place** (`714f73c`). `column_lanes` returned its 16 lanes × 32
   outputs by value; LLVM copied that 2 KB array twice per block, 72 blocks a pass. Now it fills
   the caller's buffer. V8 moves −10.7% (CI 8.6–12.6%); native moves −17%.
2. **Columns lane by lane** (`b1eaa13`). Within a block, each lane's input columns are contiguous,
   so the kernel reads weights forward instead of in 2 KB strides, which the hardware prefetcher
   follows. Native forward pass −12% to −19% on a quiet machine, moves −6% (CI crosses 1 in the
   final re-measure); V8 neutral.
3. **ReLU as a comparison** (`458687c`). `f32::max(x, 0.0)` must order NaNs and signed zeros, so for
   wasm32 LLVM scalarised every ReLU: about 12 instructions an activation, ~2 300 activations a
   pass. `if x > 0 { x } else { +0 }` agrees on every input but `-0`, whose sign nothing
   downstream reads, and vectorises. **V8 forward pass −16.6%** (replicated); native moves −7%.
4. **Memo keys a third the size** (`1f76bec`). A key held each non-zero input as index + four bytes:
   297 of an entry's 360 bytes. Now a 23-byte mask of the non-zero inputs, then one byte per value
   from a dictionary the memo builds as it meets values (71 distinct values across the corpus),
   escaped to five bytes once 255 are taken, then the legal set. Still the input exactly, so the
   same hits and misses ([Z11-69] unchanged). **Memory −24% to −30%**; native moves −10%, V8
   neutral.
5. **Native column blocks of 64 outputs** (`a8e0a7c`). AVX2's 256-bit registers hold 64 outputs'
   accumulators in eight of sixteen, as 32 do in wasm's 128-bit ones. Natively the pass waits on
   its weights, and 64 reads each input's weights as one 256-byte run. Native moves −18%, the pass
−10% (replicated);
   wasm keeps 32 (64 measured +4.8% slower in V8, 16 +12%).
6. **The module warms its search at load** (`4c25628`, spec `6551a4b`). WebAssembly has no
   on-stack replacement: the first move entered the search loop in V8's baseline code and stayed
   there for the whole search. That move is the game's widest, about 3 s. A 10 000-simulation
   search on a small fixed position at load (~11–40 ms) brings the first move from 1.154× to 0.984×
   the same move again (8 rounds each).
   A follow-up (`aa17630`) fixed its rare path. Once the 255 codes were taken, `lookup` missed
   every input with an escaped value, so the memo stopped helping (never a wrong answer). The
   corpus never reaches it; a long `serve` could. The new test stores 600 inputs past the codes;
   it caught the bug and was seen red under two mutations.
7. **Tree nodes in 24 bytes, not 32** (`93e75d8`). An expanded node's visits are always its edge's
   visits less one, so the field goes; edge indices fit 32 bits. 1.6 MB at 200 000. Time neutral
   (replay 1.02 and 0.95, moves 1.00).

8. **One host for a series' trained players** (`441cb2b`, [0011 Z11-100]). The match lanes —
   anchors, ship, pool, milestones and the gate — ran one `alphazero serve` process per player per
   game: eight workers held up to sixteen copies of the 2.5 MB weights against an 8 MB L3, and
   each game started two processes that loaded and parity checked a checkpoint. Now a series
   starts one `alphazero host` (a Unix socket, `std` only), each player of each game is a session
   on its own thread with its own memo, and every session of a checkpoint reads the one copy the
   first loaded. The answers are `serve`'s by construction and by test; the games came out
   identical. **2.0× games an hour at the anchors' 200 simulations, 2.45× at 2 000**: at 200 part
   of it is the processes no longer started, at 2 000 it is nearly all the shared cache, matching
   the 2.28× measured in one process before it was built. Five mutations seen red, in a copy.
   *Merging it moves the ladder hash* ([Z11-63]): `eval/chooser.ts` is in it, so the next milestone
   of a running run (`eighteenth`) starts afresh, though no game it plays changes.

## What was tried and dropped

| Idea | Result |
| --- | --- |
| `select`: cache `q = total / visits` on the child node | Neutral |
| `select`: 8 edges at a time, scores side by side | +35% slower: the gather branched, short nodes paid the chunk overhead |
| `select`: branchless (`select_unpredictable`) | +11% slower: the visited/unvisited branch predicts well |
| `select`: visits and totals moved into the edge arrays (contiguous scan) | Neutral (replay 1.009, 1.006; moves 1.008, 1.04), and +12 bytes an edge |
| … plus a vectorisable scan over them | Slower; LLVM does not vectorise the `u32`→`f64` conversions |
| … plus `q` cached per edge | Neutral |
| `select` without divisions: scores from a table of reciprocals, the leader taken when its margin provably exceeds the error, else the exact scan | Neutral (native 0.98, 1.02; V8 1.03) |
| `select` with 4 independent running maxima (break the compare chain) | −1.5 to −2% of the search alone natively, ≈0.3% of a move; V8 1.03 and 0.99: not worth the code |
| Browser memo kept per seat through a round (as `serve` keeps it) | Only −3.3% network calls at 100 000; a spec change ([T12-3]) for little |
| Activations sized for width 256 instead of 1024 (less zeroing) | Neutral in V8: `memory.fill` is cheap |
| Value head's first layer in the sparse column form | Native +7.5% slower (replicated), V8 mixed |
| Native blocks of 128 outputs | Worse than 64 (−6% vs −10% on the pass) |
| Weights aligned to 64 bytes in wasm | Neutral |

Six `select` variants all failed. Its cost is ~16.6 edges a call, 33.7M calls on 50 moves at
100 000 (depth ~5.6). Neither the divisions, the node loads, the branch nor the compare chain alone
is what limits it.

## Where the time goes now

- **V8:** about 70% is the forward pass's column kernel. It is at its arithmetic floor: 128-bit SIMD
  without FMA, which bit-exactness forbids, is 16 vector operations per 32 multiply-adds, twice
  AVX2's. About 12–16% is the search's tree walk, the rest the fold, the policy head and the
  sparse input list.
- **Native:** about 60% is the kernel, which is bound by memory, not arithmetic. The weights are
  2.5 MB and L2 is 512 KB, so each pass streams ~1.3 MB from L3. Under the load this machine had,
  a pass took ~730k cycles against ~40k of arithmetic. About 20% is the search's tree walk.

## Larger levers left, each a decision for you

- **Self-play** already shares one `Network` across its threads in one process; the host was the
  match lanes' missing half of that, and is done (item 8).
- **FMA / relaxed SIMD.** Would roughly halve the kernel's vector operations in V8, but changes
  every bit ([Z11-10]): a new parity regime and spec change.
- **Threads in the browser** (a pass's 8 output blocks across workers). Needs `SharedArrayBuffer`,
  so COOP/COEP headers on the deployed page.
- **AVX-512** natively: this CPU has it, but `+avx2` alone is pinned by [Z11-2]/[Z11-47] for
  portability.

**This lane does not show the speed-up, and it cannot.** Within the one run, pass 2 did the same
moves as pass 1 in 92% of the time at 10 000 and 81% at 100 000 (median per move): the run started
while the 15-minute load average was still 74, the `eighteenth` loop having just stopped, so its
first pass carried that residue. A sequential lane moves by more than this branch's whole gain
between passes of itself; the paired figures above are the measure of speed. What the lane does
establish is the budgets and the memory: at the default every pass is inside p95 3 s, p99 5 s and
10 s, and memory is down by a quarter to a third. At `quick` one move of pass 1 took 1 094 ms
against the 1 000 ms bound (position 702, round 4); pass 2's slowest was 950 ms.

Rerun at `quick` alone (10:05, load 2.08 at the start and 7.7 at the end, the desktop busy): pass 1
p95 452, p99 637, max 1 634 ms; pass 2 p95 387, p99 514, max 900 ms. That is again over the bound
in pass 1 only, and on another position: 1 224 here, 702 before. Each over-a-second move happens
once, in a first pass, and the same position takes 0.48–0.81 s in the other three passes. Four
passes held 2, 0, 2 and 0 moves over a second. Those are interruptions, not slow positions. The
clean passes are inside the bound, and pass 2 is below 10-27's record at p95 (387 against 464 ms)
and p99 (514 against 594). But `quick`'s worst move sits within 10–20% of its 1 s bound, and a
single interruption breaks it, which matters to a budget meant to hold on a person's machine.

## Method, and what it taught

- The machine was never idle. Other sessions ran an 8-worker anchors rating, then the `eighteenth`
  training run (8 workers): load average from ~10 to ~340. A forward pass took 45 µs at load 10 and
  230 µs at load 170. Sequential A/B runs were useless.
- So every comparison was **paired in one process**. Natively, both crates were linked into one
  binary (the baseline renamed); in V8, both modules instantiated side by side. They alternated
  per position, with thread CPU time and a bootstrap over positions. Search-only changes used a
  **replay** harness, answering every network call from a table recorded once, so the tree walk is
  measured without the network's noise. The kernel had its own micro-benchmark, natively and in
  V8.
- **A measurement bug, found and fixed.** The native baseline was extracted with `tar`, which keeps
  commit-time mtimes, so cargo sometimes judged it unchanged and kept an older build. The native
  per-change figures above come from a re-run with fresh mtimes (`tar -m`), each change against
  its own parent. The V8 and replay figures were unaffected.
- **The same mtime trap, again, in the host's mutations.** Restoring a mutated file with `mv`
  from a copy made before the mutation leaves it older than the mutated build, so cargo kept the
  mutated binary and a pristine copy read red. Each mutation's own result stood (the mutated
  write is always newest); the baseline was re-run after a `touch` and was green. Any harness
  that restores a file must touch it.
- Single-run bootstrap intervals are optimistic when load drifts within a run. A change was kept
  only if it replicated, or was deterministic (memory).
- Profiles: `sample`, Instruments' Time Profiler through Xcode's `xctrace` with per-instruction
  attribution, and `node --cpu-prof` for V8. Reading the wasm assembly LLVM emits is what found
  the scalarised ReLU.

The harnesses are scratch code outside the repo (`perfbench`, `pair`, `wasmbench.mjs`,
`wpair.mjs`, `wmicro`). Say if you want them kept as `examples/`.
